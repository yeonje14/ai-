# 백로그 14 제안서 · 정식 인증과 사용자별 요청 제한

세 가지 결정은 사용자 승인 후 DESIGN §9·12.2·15.3에 반영했다. 아래는 승인 당시의 제안과 후속 단계 계획이다. 기준 커밋 `a19aa20`. 통제된 졸업작품 시연에서 운영자가 초대한 참가자를 식별하고, 한 참가자의 병렬 제출·재전송·자격 증명 교체가 다른 참가자의 대기 자리를 소진하지 않도록 한다. 아래에서 기존 기본값으로 명시한 값 외의 기간·상한은 모두 **초기 제안값**이다.

## 1. 현재 동작과 설계 문서의 차이

| 근거 | 코드에서 확인한 동작 | 설계에 주는 제약 |
|---|---|---|
| `server/api/analyses.py`의 `owner_hash`, `_owned_job` | 서버는 클라이언트가 정한 16~256자 문자열을 SHA-256으로 해시한다. 조회·결과·DELETE는 그 해시와 작업 ID가 일치해야 한다. 형식 미달은 401, 타인·없는 작업은 같은 404다. | ID만 아는 사람을 차단한다. 같은 토큰을 가진 두 사람은 구분할 수 없고, 새 토큰을 무제한 만들 수 있다. 사용자 등록·만료·폐기·복구 수단이 없다. |
| `app/lib/main.dart`, `api/analysis_api.dart`, `app.dart`, `config.dart` (모두 app/lib 아래) | 서버 모드는 기본적으로 Random.secure로 만든 32자리 16진수 토큰을 API 객체에 보관한다. 현재 ID도 화면 상태에만 있고 기본 1초 주기로 조회한다. 취소 전 상태와 강한 ETag를 가져온다. 429와 503을 모두 대기열 포화로 표시한다. | 새로고침하면 토큰과 ID를 함께 잃는다. 자격 증명을 복원해도 ID를 찾을 수단이 필요하다. |
| `server/jobs/queue.py`의 `enqueue`, `claim`, `_tx` | WAL DB에서 BEGIN IMMEDIATE로 전체 queued 수 확인과 INSERT를 묶는다. POST마다 새 UUID다. Worker는 processing 1건, FIFO 선점, lease·heartbeat·재시도 및 소유 Worker 조건부 쓰기를 사용한다. | 현재의 중복 **실행** 방지와 HTTP 재전송에 의한 중복 **등록**은 별개다. 계정당 상한과 접수 이력은 없다. |
| 같은 파일의 `cancel_or_delete`, `lifecycle_etag` 및 `server/api/analyses.py` | 소유권 조회 후 같은 쓰기 트랜잭션에서 If-Match를 비교한다. active 동안 ETag가 같고 종료 시 바뀐다. 조건 없는 DELETE와 별표도 허용한다. active는 202, 종료는 폴더 정리 후 204, 정리 실패는 500이다. | 취소 접수 시점에 자리를 돌려주면 Worker 정리 전에 새 요청이 들어온다. |
| `server/api/__init__.py`, `health.py` | CORS는 설정한 출처, 기존 헤더와 메서드만 허용하고 ETag를 노출한다. 쿠키 자격 증명을 허용하지 않는다. health는 생존 여부만 공개한다. | §12.2의 인증된 주체·사용자별 제한은 목표다. §9가 허용한 여러 오류 중 현재 구현은 타인 404, 포화 429를 사용한다. §14.1의 강제 종료 미검증 표기는 최신 HANDOFF보다 이전 기록이다. |

## 2. 인증 대안과 권고

| 방식 | 시연 운영 | 복구와 비용 |
|---|---|---|
| **A. 운영자 등록 계정 + 서버 발급 개인용 불투명 Bearer 키** | 참가자별 계정을 사전에 만들고 개별 전달한다. 분석 API가 매 요청 키의 유효성과 계정을 확인한다. 앱 공통 키와 공개 가입 경로가 없다. | 같은 계정으로 재발급하면 작업을 다시 찾는다. 복구 시 운영자가 참가자를 대면 확인해야 한다. 키를 복사한 사람은 폐기 전까지 그 참가자로 동작한다. |
| B. 로컬 계정 + 암호 로그인 + 서버 세션 | 같은 SQLite에 계정, 메모리 비용이 있는 암호 해시, 만료·폐기 가능한 세션을 둔다. 운영자가 초기 계정을 발급한다. | 반복 로그인은 편하지만 로그인 시도 제한, 암호 재설정, 세션 발급·종료 경로가 추가된다. 웹 쿠키를 채택하면 CSRF와 출처 정책도 검증해야 한다. |

**A를 추천한다.** 확인할 신원은 시연 명단의 참가자이고, 계정 발급·복구를 운영자가 직접 처리할 수 있다. 외부 인증 서비스나 별도 제한 서버는 필요하지 않다.

- 운영자 전용 로컬 명령으로 임의의 고정 `user_id`를 발급한다. 이름·메일을 API나 작업 테이블에 저장할 필요가 없다. 서버가 보안 난수 32바이트를 생성해 URL-safe 문자열로 한 번만 표시한다. 명령 인자·셸 이력·환경 파일·앱 빌드에 원문을 넣지 않는다. 개별 보안 채널로 전달한다.
- `users(user_id PK, disabled_at)`, `credentials(digest PK, user_id FK, expires_at, revoked_at)`. 고엔트로피 키의 SHA-256 digest만 저장한다. 발급 후 24시간 절대 만료, 자동 연장 없음. 재발급은 같은 사용자에 새 키 발급과 이전 키 폐기를 한 트랜잭션에 묶는다. 계정 정지는 모든 키에 즉시 적용한다. 인증 만료는 Worker 작업을 취소하지 않는다.
- 모든 분석 API는 `Authorization: Bearer …`를 요구한다. 누락·형식 오류·만료·폐기·정지·구 헤더 단독은 같은 401과 일반적인 Bearer challenge로 응답한다. 신구 헤더를 함께 보내도 401로 거절한다. 클라이언트가 전달하는 사용자 ID는 권한 결정에 쓰지 않는다.
- Flutter 웹 시연에서는 키를 메모리에 두고 새로고침·앱 재시작 시 다시 입력한다. 브라우저 영구 저장소에 키를 넣지 않는다. 네이티브 자동 로그인은 후속 선택 사항이며 OS 보안 저장소와 대상별 삭제·백업 동작은 확인 필요다. 공용 단말의 로그아웃은 키·목록·결과·진행 중 재시도 상태를 메모리에서 지우고, 늦게 도착한 이전 계정 응답을 버린다. 로컬 로그아웃과 서버 키 폐기는 별개다.
- 인증 후 `GET /api/v1/analyses`가 본인 작업만 최근순으로 반환한다(200, 항목에 ID·생성 시각·작업 상태, 빈 목록은 200). 기본/최대 20건, 다음 페이지는 마지막 (created_at, analysis_id) 기준, 모든 페이지에서 사용자 조건을 다시 적용한다. 삭제한 작업은 제외한다. Flutter는 선택한 ID로 기존 상태·결과 API를 호출한다. 재발급 뒤에도 목록이 복원된다.

## 3. SQLite 접수·제한 계약

**개인별 활성 상한을 먼저 확보하고 시간 구간의 접수 횟수도 제한한다.** 기존 전체 기본값은 processing 1, queued 3이다. 아래 제한은 서버 시각 기준이며 동일 DB의 모든 API 프로세스에 합산한다.

| 용도 | 키와 초기 제안값 | 저장과 만료 |
|---|---|---|
| 분석 비용 | user_id당 queued + processing 최대 1건. 신규 접수 최대 6건/최근 10분 | jobs(user_id,job_status) 인덱스로 활성 수 조회. 별도 접수 이력에서 accepted_at이 (현재−600초, 현재]인 건수를 센다. 취소·삭제·재발급으로 환급하지 않는다. Worker 재선점은 새 접수가 아니다. |
| API 반복 호출 | 인증 성공한 user_id당 분석 API 전체 180회/고정 UTC 1분. 상태·결과·목록·DELETE·POST 및 중복 재전송 포함 | 동일 DB의 (user_id,minute) PK 카운터를 원자적으로 증가. 결과가 404·412·개인/전체 포화여도 요청량에 포함한다. 분 경계에서 연속 버스트가 가능하다. health와 CORS preflight는 제외한다. |
| POST 재전송 | 필수 Idempotency-Key는 사용자 동작마다 무작위 UUID 하나. 같은 동작 재시도에는 같은 키. 유효기간 24시간 | receipts(user_id,key,video_id,analysis_id,accepted_at,deleted), PK(user_id,key), 인덱스(user_id,accepted_at). accepted_at 기록이 접수량 원장도 겸한다. 삭제 시 같은 트랜잭션에서 영상·작업 식별자는 비우고 삭제 표식과 시각·키만 보존한다. |

1. DB 잠금을 획득한 뒤 현재 시각으로 인증을 확인한다. HTTP 요청량은 짧은 별도 쓰기 트랜잭션으로 계산·커밋한다. 이를 넘으면 `429 request_rate_limited`, Retry-After는 다음 분까지의 올림 초다. 이 단계는 작업 ID 존재를 읽지 않는다. 인증 없는 대량 트래픽은 이 제한의 보호 대상 밖이다.
2. POST는 URL을 기존 함수로 정규화하고 키 형식을 검사한다(422). 단일 BEGIN IMMEDIATE 안에서 시각을 다시 읽어 인증을 재확인한 뒤 같은 사용자·키의 **미만료** 영수증을 먼저 찾는다. 같은 video_id이면 최초 접수 응답 202와 같은 ID를 반환한다(queued는 최초 응답의 스냅샷, 현재 상태는 GET). 다른 video_id는 409 `idempotency_conflict`, 삭제 표식은 본인에게만 410 `analysis_deleted`. 다른 사용자의 같은 키는 독립이다. 키 만료 뒤 재사용은 새 접수이며 클라이언트는 자동 재전송을 중단한다.
3. 새 요청에 개인 활성 상한 → 시간 구간 접수 상한 → 전체 queued 상한 순으로 적용한다. 각각 429 `user_active_limit`, `user_submission_limit`, 기존 `queue_full`이다. 시간 제한에는 가장 오래된 유효 접수의 만료까지 Retry-After를 준다. 자리 제한은 완료 시각을 예측할 수 없어 헤더를 생략한다. 다른 사용자의 ID·순번·남은 자리 수는 반환하지 않는다. 전역 포화 여부 자체는 429로 드러난다.
4. 통과하면 jobs와 receipts를 한 번에 INSERT·커밋한 뒤 202. 응답 유실 뒤 재전송도 한 번만 접수된다. 예외는 둘 다 롤백하고 DB 잠금 제한시간 초과는 503 `temporarily_unavailable`로 반환한다. 인증·제한 DB 장애 시 허용으로 대체하지 않는다. 요청량 카운터는 앞 단계에서 이미 기록된다. 만료 영수증은 동일 키 재사용 전 트랜잭션 내 제거한다. 정기적으로 24시간 지난 영수증과 지난 분 버킷을 소량씩 정리한다. 계정당 상한은 재발급·프로세스 재시작 뒤에도 유지된다. 시간 동기화된 단일 호스트를 전제로 하며 시계 역행은 운영 경보 대상으로 둔다.
5. Worker는 현행 FIFO와 단일 processing, lease 소유자 비교, heartbeat, attempts 및 복구 정리를 유지한다. cancel_requested 중에도 active이며 종료 커밋 후 개인 자리가 열린다. 여러 계정을 가진 한 사람의 독점은 운영자의 중복 발급 통제로 다룬다.

## 4. 경합·노출·전환

- 상태·결과·목록은 동일 DB 읽기 스냅샷에서 인증과 소유자 필터를 적용한다. DELETE는 기존 cancel_or_delete의 쓰기 잠금 안에서 **인증 → 소유권 → If-Match → 상태 전이**를 수행한다. 폐기·만료가 먼저면 401, 타인·삭제됨은 404, 본인 조건 불일치는 본문 없는 412다. 유효성 판단 시점 뒤에 만료·폐기돼도 이미 승인한 원자적 작업은 유효하다. 취소가 먼저면 기존 202와 Worker 정리, 종료가 먼저면 오래된 active 태그로 412다. terminal ETag로 동시 삭제하면 204 한 번, 다음은 404다. 정리 실패는 500과 기존 행 보존이다.
- Flutter는 401에서 폴링 중지·재인증 후 목록 복원, 429 시간 제한에서는 Retry-After만큼 대기, 활성 상한에서는 기존 작업 열기, 503에서는 일시 장애를 표시한다. 취소의 412는 상태 재조회이며 무조건 DELETE로 재시도하지 않는다. 15초 클라이언트 타임아웃 뒤 같은 동작에만 기존 접수 키를 재사용한다. 앱 재시작으로 키를 잃었으면 목록을 먼저 확인한다.
- 소유자·ID 복합 조건을 GET·DELETE·결과·목록·영수증에 동일 적용한다. 타인과 없는 ID의 응답 본문·헤더·코드는 같게 하고 절대 시간 동일성까지 보장한다고 주장하지 않는다. 모든 인증 응답 및 오류에 no-store. 오류에 입력·SQL·검증 원문을 포함하지 않도록 FastAPI 기본 validation 오류까지 점검한다. 서버·프록시·Flutter 로그는 헤더/본문/쿼리를 기록하지 않고 경로 템플릿·코드·시간만 남긴다.
- 설정된 CORS 출처만 Authorization, Idempotency-Key, Content-Type, If-Match와 기존 메서드를 허용하고 ETag·Retry-After를 노출한다. 쿠키 미사용. 시연은 루프백 또는 접근 제한 HTTPS로 운영한다. 외부 공개 전에는 실제 배포에서 TLS·출처·로그 마스킹, 무인증 요청 폭주에 대한 앞단 제한, 계정 발급/회수·분실 대응, DB 접근권한·백업/복원 시 폐기 키 부활 방지, 폴링량과 SQLite 잠금이 heartbeat에 주는 영향을 검증한다. 프록시의 실제 로그 기본값과 브라우저 동작은 확인 필요다.
- 전환은 유지보수 시간에 신규 접수 중지 → 기존 작업 drain 및 소유자 정리 기회 제공 → API·Worker 정지 → 기존 DB/런타임을 접근 제한 상태로 분리 보존 → 새 스키마 DB·별도 runtime에 사용자 FK가 필수인 jobs로 시작한다. 구 토큰을 새 사용자에 자동 연결하지 않는다. 구 기록은 새 목록에 나오지 않음을 공지하고 보존 종료일은 운영자가 정한다. 전환 실패 시 신규 쓰기 전에는 원래 DB·바이너리로 복귀한다. 신규 접수 후에는 두 DB를 섞지 않고 새 쓰기를 멈춘 뒤 복구한다. API·Flutter·smoke 클라이언트를 함께 전환하고 열린 레거시 인증 경로를 두지 않는다.

### §15.3에 제안할 결정 문안 (미승인)

백로그 14의 통제 시연은 운영자 등록 사용자와 서버 발급·폐기 가능한 Bearer 자격 증명을 사용한다. 작업 소유권과 요청 제한은 고정 사용자 ID에 연결한다. 사용자별 목록을 추가하고 분석 POST에 Idempotency-Key를 요구한다. 인증 실패는 401, 타인과 없는 작업은 404, 동일 키의 충돌·삭제 이력은 409·410, 제한은 원인을 구분한 429로 반환한다. 접수와 개인·전체 상한 검사는 SQLite 트랜잭션으로 직렬화한다. §9의 수명주기 ETag·조건부 DELETE, §10의 상태·점수, Worker의 선점·재시도 정책은 유지한다. 인증·제한 오류는 분석 결과나 작업 상태로 기록하지 않는다.

## 5. 수용 테스트 계획

‘기존’은 기준 커밋의 테스트가 다루는 동작이다. 인증 헤더·라우트 목록 fixture를 새 계약으로 바꾼 후에도 같은 단언을 유지한다. ‘신규’는 구현 시 추가할 테스트다.

## 6. 구현 순서와 완료 조건

1. **계정·폐기·전환 도구.** 신규 스키마, 운영자 발급/재발급/정지 명령과 구 DB 분리 절차를 만든다. 완료 조건은 발급 원문 비저장, 재시작 뒤 만료·폐기 유지, 구 DB 보존 리허설 통과다.
2. **API 소유권.** 모든 분석 경로에 같은 사용자 판별을 붙이고 본인 목록·페이지 조회를 추가한다. 완료 조건은 401/404 일관성, DELETE 잠금 경합 테스트와 기존 ETag·취소·정리 테스트 통과다.
3. **접수·중복·제한.** 원장, 요청 버킷, 인덱스, 만료 정리와 오류 계약을 반영한다. 완료 조건은 두 API 프로세스의 병렬 접수와 재시작 테스트에서 상한·영수증·작업 수 일치, Worker 재시도 무과금이다.
4. **Flutter 및 검증 클라이언트 전환.** 키 입력/지우기, 본인 작업 복원, 중복 키 재사용, 제한별 안내를 구현한다. 완료 조건은 새로고침·재인증·412·429 흐름, 보호 라우트 목록과 CORS 테스트, 모의 및 격리 API 스모크 통과다.
5. **시연 인수.** 두 참가자로 복구·독점 방지·폐기·오류 로그를 확인하고 정상 폴링과 부하에서 DB 잠금, heartbeat 지연, 429 비율을 측정한다. 완료 조건은 §5 표의 결과와 실측에 따른 상한 유지/조정 근거를 HANDOFF에 기록하는 것이다.

## 7. 승인할 결정

1. 시연 인증을 운영자 등록 개인 Bearer 키로 할까? **A 권장.** 절대 만료 24시간, 운영자 재발급, 웹 재실행 시 재입력을 함께 채택한다.
2. 접수 정책을 개인 활성 1건·10분 6건·전체 API 분당 180회로 시작할까? **이 초기값과 24시간 재전송 보호를 권장한다.** 기존 전체 대기 3건·실행 1건을 유지하고 시연 인수 때 수치를 재검토한다.
3. 구 작업의 계정 이전 없이 새 DB로 전환할까? **기존 작업 drain·분리 보존 후 전환을 권장한다.** 새 계정으로 만든 작업부터 목록으로 복구하며 전환 전에 구 기록 보존 종료일을 정한다.
