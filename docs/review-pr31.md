## 발견

1 | 중간 | 키가 없거나 틀린 요청도 키 확인 전에 DB 쓰기 잠금을 잡아서, 이런 요청이 몰리면 정상 요청과 Worker heartbeat가 밀리고 401 대신 503이 날 수 있음 | 코드(먼저 잠금 없이 키 확인, 맞을 때만 쓰기 잠금) + 테스트

2 | 중간 | 검증 스크립트 3개(`verify_real_worker_lifecycle`, `smoke_gate_worker`, `smoke_cancel_worker`)가 옛 `X-Client-Token`을 쓰고 계정 DB 없이 서버를 띄워 지금은 실행되지 않음 | 코드(`smoke_slice --isolated`처럼 계정 DB·키 발급·Bearer·접수 키로 전환) + 테스트

3 | 중간 | DESIGN §9 머리말이 아직 "X-Client-Token 사용"이고, 목록 엔드포인트·reason_code 8종·`WWW-Authenticate`가 빠져 있음. 403·503 설명이 코드와 다르고, §14.1과 README는 "미구현"으로 남아 있음 | 문서 + §15.3 결정(API 계약 문구를 바꾸므로 결정 기록 갱신을 먼저 제안)

4 | 중간 | 문서의 서버 실행 방법대로 하면 서버가 시작하지 않음(계정 DB 초기화와 0700/0600 권한 단계 누락, curl 예시가 옛 헤더라 401) | 문서(DESIGN 하단, README, `app/README.md`)

5 | 낮음 | 서버 시계가 뒤로 가면 "10분에 6건" 접수 한도를 우회할 수 있고, 시계 역행 경보도 없음 | 코드 + 테스트. 역행 처리 방식(워터마크·경보)을 정하는 §15.3 결정이 필요할 수 있음

6 | 낮음 | Flutter에서 다른 키로 다시 인증해도 앞 사용자의 Retry-After 대기(최대 600초)가 남아 새 사용자의 접수를 막음 | 코드(Flutter `setCredential`에서 재시도 상태 초기화) + 위젯 테스트

7 | 낮음 | 문서대로 실행하면 uvicorn access log가 켜져 목록 커서 쿼리가 로그에 남음(키는 남지 않음) | 문서(실행 명령에 `--no-access-log`) 또는 코드(로그 필터)

8 | 낮음 | Worker는 계정 DB인지 확인하지 않고, 경로가 없으면 옛 형식 DB를 새로 만들어서 API와 Worker가 다른 DB를 조용히 쓸 수 있음 | 코드(Worker도 API와 같은 DB 검사, DB 생성 금지) + 테스트

9 | 낮음 | Flutter가 모든 422를 "YouTube 주소 아님"으로, 409·410·503을 일반 서버 오류로 안내함 | 코드(Flutter reason_code별 문구) + 테스트

10 | 정보 | 옛 형식 DB 거부 테스트가 의도한 검사(application_id)가 아니라 파일 권한 검사에서 걸려 통과함. 코드 자체는 정상 | 코드(테스트에서 파일을 0600으로 바꾼 뒤 검증)

11 | 정보 | 스키마 설치 여부를 `receipts` 테이블 유무로만 판단해서, 트리거·인덱스가 빠진 DB를 고치지도 거부하지도 않음 | 코드(필수 객체 존재 확인)

12 | 정보 | DB 오류를 500/503으로 바꿀 때 로그를 남기지 않아 원인을 진단할 수 없음 | 코드(예외 종류와 코드만 로그)

13 | 정보 | 분당 한도가 고정 1분 창이라 분 경계에서 1~2초 사이에 최대 360회가 통과함. 제안서에서 받아들인 사항 | 바꾸지 않아도 됨. 바꾸려면 §15.3 결정 + 코드(슬라이딩 창)
