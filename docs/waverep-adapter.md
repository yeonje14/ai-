# WaveRep 어댑터: 샘플링·배치 측정 결과

README §14.1 백로그 7번의 앞부분(어댑터). 측정일: 2026-11-12(CPU 3건), 2026-11-13(나머지 11건).

> **이 문서는 속도·재현성 확인이다. 성능 검증이 아니다.**
> 테스트 영상에는 **발화가 없다**(본인 얼굴, 주변 소리만). 이번 작업은 발화 여부와 상관없이
> 어댑터가 같은 입력에 같은 점수를 내는지, 얼마나 걸리고 메모리를 얼마나 쓰는지만 본다.
> 점수는 모델의 원시 logit이다. 확률도 판정도 아니며 임계값을 적용하지 않았다. `overall_score`는 계속 `null`이다.
> Gate와 Worker에는 연결하지 않았다.

## 결론

- 어댑터(모든 프레임, CPU, 배치 1, `pretrained=True`)의 프레임 점수는 스파이크의 `cpu-1` 결과와 **완전히 같다**(313프레임 최대 절대차 0.0).
- **`pretrained=False`로 만들어도 점수가 같다**(313프레임 최대 절대차 0.0). 빈 Hugging Face 캐시 + `HF_HUB_OFFLINE=1`에서도 `pretrained=False`는 동작했고, `pretrained=True`는 실패했다. 어댑터 기본값을 `pretrained=False`로 했다.
- 같은 설정을 두 번 실행하면 점수가 완전히 같다(CPU 배치 8, MPS 배치 8 각각 최대 절대차 0.0).
- 배치로 묶으면 점수가 아주 조금 달라진다: CPU 배치 1 대 8 최대 0.000037, MPS 배치 1 대 8·16 최대 0.00000095. CPU 대 MPS는 최대 0.00019(스파이크와 같은 수준). 어느 비교에서도 0을 기준으로 부호가 바뀐 프레임은 없다.
- 샘플링으로 고른 프레임의 점수는 "모든 프레임" 실행의 같은 프레임 점수와 같다(MPS는 차이 0.0, CPU는 초당 4장에서만 최대 0.0000062. 배치에 함께 묶인 프레임이 달라진 경우다).
- **MPS에서는 배치 1이 가장 빨랐고 메모리도 가장 적었다**(약 6.2장/초, 드라이버 할당 0.70 GiB). 배치 8·16은 약 3.8~4.0장/초, 드라이버 할당 1.70 GiB였다. 배치를 키워도 빨라지지 않았다. 배치 1은 1회 측정이다. 어댑터 기본 배치 크기를 1로 했다.
- 샘플링은 실행 시간을 프레임 수에 거의 비례해 줄인다. 10.43초 영상에서 MPS 전체 시간은 모든 프레임 56~90초, 초당 4장 18초, 2장 12초, 1장 9초였다.

## 입력과 환경

- 영상: `data/research/samples/KakaoTalk_Video_2026-11-12-14-34-16.mp4` (Git 제외). 저장소 소유자가 직접 촬영한 본인 영상. HEVC 1920×1080, 30fps, 313프레임, 10.43초. **발화 없음.** 권한 근거와 형식은 `docs/waverep-spike.md` "입력"과 같다.
- 구간: 영상 전체를 한 구간으로 주었다.
- 기기·패키지·원본 코드·가중치: `docs/waverep-spike.md` "환경"과 같다(Apple M3 16GB, torch 2.15.0, 원본 커밋 `0fd6010`, `weights_dinov2_G4.ckpt`).
- 영상 내용과 프레임 이미지는 문서와 결과 파일에 넣지 않았다. 이 영상은 학습 데이터로 쓰지 않는다.

- 원본 저장소(`research/waverep/upstream/`)는 수정하지 않았다. 전처리는 원본 `create_transform`을 그대로 쓴다(가운데 504×504 crop, ImageNet 정규화, 리사이즈 없음). 모델 생성만 어댑터 쪽에서 한다. 원본 `create_model`은 `pretrained=True`가 고정이기 때문이다. 아키텍처, crop 크기, 키 걸러내기, `strict=True` 로드는 원본과 같다.
- 모델 프로세스에는 작업 폴더 안의 요청·결과 JSON 경로 두 개만 넘긴다. 두 파일은 실행이 끝나면 지운다. 프레임 이미지는 디스크에 쓰지 않는다.
- 장치는 `cpu`·`mps`만 받는다. `mps`를 쓸 수 없으면 추론 프로세스가 `cpu`로 대체하고 `model.device_used`에 적는다. `PYTORCH_ENABLE_MPS_FALLBACK=1`을 설정한다.
- **샘플링 규칙**: 구간 `[start, end)`마다 `start + k / sample_fps` 시각의 프레임(`floor(t × fps)`)을 고른다. `sample_fps=None`이면 구간 안 모든 프레임이다. 구간이 겹쳐도 같은 프레임은 한 번만 쓴다. 영상은 처음부터 순차로 읽고, 고르지 않은 프레임은 `grab()`만 한다.
- **결과**: 프레임별 `{index, time_sec, logit}`, `raw_metrics.frame_logit`(개수·평균·중앙값·최소·최대·표준편차), 시간, 메모리, 모델 정보. `raw_score`는 `null`이다. 프레임 logit을 어떻게 집계할지 정하지 않았기 때문이다(백로그 8번 이후).
- **상태**: `completed`, `insufficient_input`(구간 없음, 고른 프레임 없음), `unsupported_input`(짧은 변 504px 미만), `error`(프로세스 실패, 타임아웃, 깨진 결과 등). 실패하면 점수는 `null`이고 예외를 던지지 않는다.

## 측정 결과

명령(저장소 루트, conda `trinity`):

```bash
python scripts/bench_waverep_adapter.py --video data/research/samples/KakaoTalk_Video_2026-11-12-14-34-16.mp4
```

실행 이름은 `장치-샘플링-배치`다. `all`은 모든 프레임, `fpsN`은 초당 N장, `r2`는 같은 설정의 두 번째 실행이다. `pretrained` 표시가 없는 실행은 모두 `pretrained=False`다.

- 각 설정은 1회(일부 2회) 측정이고 다른 프로세스가 떠 있는 상태였다.

- MPS에서 최대 RSS는 배치 크기와 상관없이 약 1.0 GiB이고, 드라이버 할당이 0.70 → 1.70 GiB로 늘 때 peak memory footprint도 1.10 → 2.3 GiB로 함께 늘었다. 스파이크에서 남긴 질문("footprint가 GPU 할당을 포함하는가")에 대해, **footprint가 MPS 드라이버 할당을 반영한다는 것과 맞는 결과**다. 전부 포함하는지를 증명한 것은 아니다.
- 드라이버 할당은 배치 8과 16에서 같다(1.70 GiB). 드라이버가 한 번 잡은 메모리를 풀에 유지하기 때문으로 보이나 **확인 필요**.
- 메모리는 프레임 수(샘플링)와 거의 무관하고 배치 크기에 따라 달라진다.
- 이 기기(16GB)에서 가장 큰 값은 MPS 배치 8의 peak footprint 2.32 GiB다. 다른 해상도에서는 측정하지 않았다(crop이 504×504 고정이라 모델 입력 크기는 같다).

## pretrained=False 확인

- 스파이크의 키 대조에서 체크포인트가 모델의 177개 키를 모두 덮어쓴다는 것을 확인했다. 이번에는 실제 점수로 확인했다: `pretrained=True`와 `False`의 313프레임 점수가 완전히 같다(CPU, 배치 1).
- 오프라인 확인(2026-11-13): 빈 폴더를 `HF_HOME`으로 주고 `HF_HUB_OFFLINE=1`로 실행했다(CPU, 0~3초 구간, 초당 1장).
  - `pretrained=False`: 성공. 3프레임 점수가 `cpu-all-b1`의 같은 프레임과 최대 절대차 0.0. 빈 캐시 폴더에 아무것도 생기지 않았다.
  - `pretrained=True`: `status=error`, `reason_code=inference_error`(`LocalEntryNotFoundError`). 어댑터가 예외 없이 실패 결과를 돌려줬다.
- 그래서 어댑터 기본값은 `pretrained=False`다. 서비스 실행에 Hugging Face Hub 접근이 필요 없다.

## 테스트

`tests/test_waverep_adapter.py` (conda `trinity`, torch 없음):

- 샘플링 순수 함수: 간격, 반열린 구간 경계, 겹침, 영상 끝, 잘못된 값.
- 명령이 인자 리스트인지, `cuda` 등 허용하지 않는 장치와 잘못된 설정을 프로세스 실행 전에 거르는지.
- 가짜 추론 프로세스로 실패 격리: 비정상 종료, 깨진 JSON, 형식이 어긋난 결과, 타임아웃(프로세스 그룹 종료), 이전 실행의 결과 파일이 남아 있는 경우. 모두 `status=error`, 점수 `null`.
- 결과에 판정·확률·`overall_score` 필드가 없고 `raw_score`가 `null`인지.
- 실제 추론 1건(CPU, 2프레임). venv·가중치·샘플 영상이 없으면 건너뛴다.

`pytest -q`: 124개 통과(2026-11-13, 실제 추론 포함, 건너뛴 테스트 없음).

## 하지 않은 것과 한계

- Gate 연결, Worker 연결, heartbeat, coverage 채우기. 어댑터는 실행 중 진행 상황을 알리지 않으므로, Worker에 연결할 때 lease를 주기적으로 연장하는 방법을 따로 넣어야 한다.
- 발화가 있는 영상, 합성·조작 영상, 다른 해상도·세로 영상·가변 프레임률 영상으로는 실행하지 않았다. 프레임 시각은 `번호 / fps`로 계산하므로 가변 프레임률 영상에서 구간과 프레임이 맞는지는 **확인 필요**다.
- 짧은 변이 504px보다 작은 영상은 추론하지 않고 `unsupported_input`으로 돌려준다. 이 경로는 실제 저해상도 영상으로 실행하지 않았다(**미검증**).
- 영상 1개, 설정당 1~2회 측정이다. 시간 값은 편차가 큰 값으로 읽어야 한다.
- 전원 연결 상태의 CPU 배치 1, 배치 1의 샘플링 실행, MPS 배치 2·4는 측정하지 않았다.
- 프레임 logit의 집계 방법, 샘플링 간격, 임계값은 정하지 않았다.

## 재현 방법

환경과 가중치 준비는 `docs/waverep-spike.md` "재현 방법" 1~2단계와 같다. 그다음:

```bash
conda activate trinity
pytest -q tests/test_waverep_adapter.py
python scripts/bench_waverep_adapter.py --video data/research/samples/<허가 영상>.mp4
# 이미 결과가 있는 실행은 건너뛴다. 다시 재려면 --force, 일부만 재려면 --only <이름>
# 비교만 다시 계산: --compare-only
```

결과는 `data/research/waverep-adapter/<이름>.json`과 `comparisons.json`에 있다(Git 제외).
